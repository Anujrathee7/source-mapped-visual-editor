# AC-13 — v2 end to end

The claim v2 has to survive: **however an edit was authored, it is verified the same way.**

Playwright, driving the studio against a fixture project served by `@sve/host`, on the fake
provider. No API key, no spend, no model phrasing to flake on.

These criteria are fixed. If an implementation fails one, the implementation changes.

## AC-13.1 — v1 still passes, untouched

The 15 v1 tests keep passing exactly as written. They are the regression test for the
mechanism; v2 wraps it in a product and must not have quietly changed what it wraps.

If a v1 test needs editing to accommodate v2, that is a v2 bug until proven otherwise.

## AC-13.2 — Connect

Connect a fixture project through the studio UI. The preview renders it, and elements come
back stamped — asserted on `data-sve-loc` in the iframe, not on the page merely looking right.

The fixture is a copy, never a checked-in tree. `git status` is clean after every run,
including after a failing one.

## AC-13.3 — A clicked edit lands

Select an element in the preview, change its text, Apply.

- the override appears before any write;
- the file changes on disk at the expected line, and no other line changes;
- hot reload fires, the override lifts, and the rendered result matches;
- the change log shows one row, `landed`.

## AC-13.4 — A chat edit lands, through the same loop

Ask the agent, in the chat panel, for a concrete change to a named element.

- it proposes; **the project is byte-for-byte unchanged at that moment** — asserted on the
  files, not on the UI;
- the proposal is visible as an override in the preview;
- Apply writes, hot reload fires, the override lifts, the result matches;
- the change log shows the row as `landed`, indistinguishable in kind from AC-13.3's.

## AC-13.5 — Both are caught when wrong

With the fake provider told to write the wrong thing, **a clicked edit and a chat edit both
report `drifted`**, both show intent versus rendered, and both keep their override applied.

This is AC-5.2 extended to v2. A chat path that reported `landed` for a wrong write would be
a hole straight through the product's only real claim.

## AC-13.6 — Revert from the change log

Revert a row. The file is restored byte-for-byte, the row reads `reverted` — never `landed` —
and the preview returns to what it showed before.

## AC-13.7 — Refusal to connect is legible

A project with no Vite config, and one where zero elements were stamped, are both refused in
the UI with the reason the host gave. The second is a blocking error, not a warning: an
editor that loads and does nothing when clicked is the failure most easily mistaken for a
broken product.

## AC-13.8 — The mutation test still decides

The v1 gate, extended:

Break the lift step so the DOM is read while the override is still painted. Then **AC-13.5
must go red for both the clicked and the chat edit**, while AC-13.3 and AC-13.4 stay green.

A verifier that always reports green passes every happy path in this file. Only the
deliberately-wrong write tells the two apart, and it must do so on both authoring paths or
the chat panel is an unverified back door.

Recorded in the README with the actual output, as v1's was.

## AC-13.9 — CI runs all of it without a key

The fake provider throughout. The job needs no credential, makes no model call, and cannot
flake on phrasing. The live suites stay opt-in and never run in CI.
